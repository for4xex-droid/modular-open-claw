# ADR 031: A2C マイクロ課金における asset_id 伝搬の Phase 2 への据え置き

## ステータス
Accepted

## コンテキスト
Aiome と Nurture 間の Synergy において、クリエイターへの収益還元（A2C: Asset-to-Creator）パイプラインを実装した。
現在、A2C の主要経路は2つ想定されている：
1. **マーケットプレイスでの明示的な購入**（Stripe Checkout）
2. **LLM推論時の LoRA / スキル利用に伴うマイクロ課金**（Inference Deduction）

1 の経路については、Stripe の webhook メタデータから `asset_id` を正しく抽出し、ライセンス付与と収益分配（`RevenueSplitter`）を行うロジックが完成し稼働している。

一方で、2 の経路（`stream.rs` や `agent_engine.rs` での `deduct_generation_cost` 呼び出し）では、現在 `asset_id` が常に `None` として渡されている。
これを「デッドコード（不備）」とみなし Phase 1 で修正するか検討したが、以下の技術的・設計的課題が判明した：

- **情報源の欠如**: 現在のテキスト生成ストリームのスコープ内には、使用中の LoRA モデルやスキルの UUID を特定する手段がない。ツールコールの実行時も `skill_name`（文字列）で処理されている。
- **波及範囲の大きさ**: これを解決するには、`ToolExecutionEvent` の型変更、SSE ストリームのイベント構造変更、WASM スキルマネージャーでの UUID 逆引きなど、少なくとも6ファイル以上にまたがる大規模な改修が必要となり、コアであるチャット機能のデグレードリスクが高い。
- **意味的妥当性**: テキスト推論そのものの課金は、クリエイターのアセット使用とは無関係の LLM API コスト回収であるため、`None` を渡すこと自体はエコノミー設計として誤りではない。

## 決定
- LLM 推論パス（`stream.rs`, `agent_engine.rs`）での `asset_id` 伝搬実装を、**Phase 2（LoRA Marketplace UI 実装時）まで据え置く**。
- Phase 2 にてフロントエンドの UI が完成し、ユーザーが「どの LoRA を使うか」を明示的に選択するフローができたタイミングで、API リクエストのパラメータとして自然に `asset_id` を流入させるアーキテクチャを採用する。

## 影響
- **ポジティブ**: 今スプリントでの無駄でリスキーな大規模リファクタリングを回避し、チャット機能の安定性を担保できる。
- **ネガティブ**: Phase 2 まで、推論ごとのクリエイターへのマイクロポイント還元（1円未満の蓄積）は発生しない（ただし、マーケットプレイスでの購入によるまとまった収益還元はすでに機能するため、ビジネス上の致命傷にはならない）。

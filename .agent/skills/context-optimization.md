# コンテキスト最適化ガイドライン (Context Engineering)

AIエージェントへの情報供給をコントロールする術。コンテキストが少なすぎれば幻覚（Hallucination）を生み、多すぎればフォーカスを失う。適切なタイミングで適切な量だけを提供する。

## 🧠 5段階のコンテキスト階層

1. **Rules Files (常駐)**: `.agent/skills/` 内の規約。プロジェクト全体で常に厳守される。
2. **Specs / Architectures (機能単位)**: `docs/specs/` 等。該当タスクのセクションのみ読み込む（全読み込みは避ける）。
3. **Source Files (タスク単位)**: 修正対象のコード、関連テスト、同パターンの既存コード。事前の `view_file` リーディングが必須。
4. **Error / Test Results (イテレーション毎)**: ターミナルのコンパイルエラーやテスト失敗結果（該当箇所のみ抽出する）。
5. **History (随時要約)**: チャット履歴。スレッドが長大化して出力が劣化し始めたら、新規セッションに切り替える。

## 🚧 混乱管理パターン (Confusion Management)

仕様と実装が矛盾していたり、情報が不足している場合、**絶対にAIの推測だけで進めない**こと。「混乱」を明確に言語化し、ユーザーに判断を仰ぐ。

**❌ 悪い例 (サイレントな推測での強行)**:
（内心で「仕様はRESTだけど、今のコードはGraphQLだから、勝手にGraphQLで行こう」と決める）

**✅ 良い例 (選択肢の提示)**:
```text
⚠️ CONFUSION (矛盾・不明瞭の検知):
仕様書ではRESTとなっていますが、既存の `src/graphql/` のコードベースはGraphQLが標準となっています。

Options:
A) 仕様に厳密に従い、新しく REST エンドポイントを追加する
B) 既存のパターンに従い GraphQL を使用し、仕様書側を更新するよう提案する

→ どちらのアプローチをとりますか？
```

## 🛑 共通の言い訳 (Anti-rationalization)

| エージェント(AI)のよくある言い訳 | 現実 (Reality) |
|----------------------|----------------|
| 「AIはプロジェクトの規約を自動的に推測すべきだ」 | エスパーはできません。必ず規約ファイル(Golden Rulesなど)を読み込んでから着手してください。 |
| 「コンテキストは多いに越したことはありません」 | 情報量が多すぎると（例えば5000行以上の無関係なファイル）、AIは核心の指示を忘れやすくなります。スコープを絞ってください。 |
| 「間違えたら後でユーザーが指摘してくれるはずです」 | 修正コストは予防コストより高いです。事前に「実行プラン」を提示して方針を確認してください。 |
| 「既存コードから推測してそれっぽく実装しました」 | 推測で独自パターン（幻覚APIなど）を生み出さず、関連ファイルのパスを必ず `grep_search` や `view_file` でたどって実例に忠実に倣ってください。 |

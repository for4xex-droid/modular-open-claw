# Mission Control Principles

プロジェクトが巨大化し単一のAIエージェントのコンテキスト（記憶）で全容を把握できない場合、当てずっぽうな計画立案は致命的なシステム崩壊（カスケード障害）を引き起こします。
すべてのアーキテクチャ変更、大規模リファクタリング、新機能開発の前に、必ず以下の **4原則 (The 4 Pillars)** を実行してください。

## 1. 🔍 Deep Scan (AST Mapping)
人間のプログラマの記憶のように、LLMのコンテキスト履歴や推測に依存してはならない。
コードの変更前に必ず物理的なASTや実ファイルを抽出・スキャンせよ。

- **Action**: `grep_search`, `list_dir`, `docs/architecture/ARCHITECTURE.md` または `cargo tree` 等を駆使して、対象となる文字列やコンポーネントがどこから参照されているかを「物理的に」洗い出す。
- **Rule**: 当てずっぽうを排除し、フロントエンドからバックエンドまで波及する該当箇所を物理的に証明してから計画を立てること。

## 2. 🌊 Ripple Effect Analysis (波及分析)
ひとつの変更が引き起こすカスケード効果を多角的にトレースせよ。

- **Action**: ある変更（例: CWD / カレントディレクトリの変更、依存クレートのバージョンアップなど）を行った際、UIのエンドポイント設定、Tauriのサンドボックス権限、Dockerのボリュームマウントなど「他の層（Layer）」にどう影響するかを分析する。
- **Rule**: バックエンドの変更がフロントエンドにどう影響するか（またはその逆）を、必ず `grep_search` による実体検索と `RIPPLE_MAP.md` の両面から検証し、計画書 (`implementation_plan.md`) に明記すること。

## 3. 😈 Red Teaming (悪魔の弁護人)
計画した解決策が実稼働環境でどうクラッシュするかを「攻撃者（あるいは最悪のシナリオ）視点」で検証せよ。

- **Action**: 「Tauri環境」「本番のDockerコンテナ内」「CI/CDパイプライン」など、ローカルで動くだけではなく実際のデプロイメント環境で発生しうる障害（権限エラー、パス不在、同時実行ロックなど）を事前に洗い出す。
- **Rule**: なぜその計画が失敗するのかを自問自答し、防御策（Defensive Programming）やフォールバック手段を組み込むこと。

## 4. 🗂️ Drop-Dead GC (Noise Reduction)
使わないコードや非推奨のコンポーネントは、コンテキストを汚染し判断を鈍らせる最大のノイズである。

- **Action**: プロジェクトの目的（MVPなど）から外れたレガシーコード（例: `napi-bridge`, 古いスクリプト等）は、スコープから完全に落とす。可能であれば削除するか、`.ignore` に追加して視界から消すこと。
- **Rule**: YAGNI (You aren't gonna need it) を徹底し、不要なコードや関係のないリファクタリングに工数とコンテキストを浪費しないこと。

---

> **絶対に忘れないための制約**: 
> AIエージェントは自らの「理解しているつもり」を疑え。「私はこのリポジトリを完璧に理解している」という錯覚こそが最大のバグを生む。常にこの4原則に立ち返り、物理的証明に基づくコーディングを行うこと。
